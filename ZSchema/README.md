# ZSchema — HotChocolate binding (`IZ.Schema`)

Turns the ZCore descriptor IR into a GraphQL schema and wires the batching resolver. Nothing here
uses HotChocolate's `[UseProjection]`/`[UseFiltering]`/`[UseSorting]` attributes or its built-in
`DataLoader` classes; the codebase has its own equivalents.

## How a type/field becomes GraphQL

- A new `ZQueryBase`/`ZMutationBase`/`ZSubscriptionBase` class is only part of the API once the
  consuming project's registration aggregate exposes it as a public property (Chordzy:
  `TuneQuery`/`TuneMutation`/`TuneSubscription`, hung off `TuneRequest`) **and** the type map under
  `<Project>/Types` has been regenerated by running the Development server. Miss either and the
  class still compiles with no complaint. `.claude/hooks/ApiRegistrationGuard.cs` and
  `ZTests/ZApiRegistration` check the first; a test asserting `ZApi.GetMethodImplementor(...)`
  contains the class checks the second.
- `ZSchema.AddSchemaQuery` registers `ZQueryType`/`ZMutationType`/`ZSubscriptionType` (one field
  per method on `ZQueryBase`/`ZMutationBase`/`ZSubscriptionBase` subclasses) and one
  `ZObjectType<T>` per `ZApi.TypeMap.ApiObjects` entry. Binding is **explicit**
  (`DefaultBindingBehavior = Explicit`): only descriptor properties/methods become fields.
  `AddFiltering()`/`AddSorting()` are registered but no field uses them; paging options
  (`MaxPageSize 100`, `DefaultPageSize 10`) apply only to fields that opt in (none today).
- `ZObjectType<T>.Configure` → `AddZRequestProperty` (field resolver = `prop.GetValue(parent)`,
  i.e. a plain getter) and `AddZRequestMethod` for methods (resolver invokes the C# method with
  converted args; a `Task`/`IZResult` result is awaited). So a GraphQL field like
  `song { scores { parts } }` calls `Song.GetScores()` → `ResolveArray<Score>(...)` per song.
- Queries are executed only through **persisted operations** (`UsePersistedOperationPipeline`,
  `ZQueryAccessor : IOperationDocumentStorage`): the client sends an id such as
  `Query|songs|Full`, `ExecutionPlan.Load` expands it using the fragments in `TuneWeb/User/GraphQL`
  (`[ApiFormat]` formats). Ad-hoc queries are not accepted — any new field must be reachable
  from a fragment, which is why `TuneHostApp.GenerateSourceFiles()` regenerates fragments in
  Development.
- `ZDataTypeInspector` hides `[OutputIgnore]` members and `IAmInternal` types;
  `ZNamingConventions` camel-cases; `GraphqlErrorFilter` maps exceptions to status codes;
  `ApiExecutionEventListener` emits per-operation diagnostics.
- Enums bind via `ZEnumType<T>` as GraphQL enums whose values are only the *declared* members —
  a `[Flags]` combination (e.g. `A|B == 3`) has no name: `EnumType.Serialize` throws and variable
  coercion rejects numbers. Flags enums therefore never cross the wire: `[OutputIgnore] +
  [InputIgnore]` on the property, numeric `*Val` mirror instead (`../Docs/data-design.md` §1).
  `options.EnableFlagEnums = true` in `ZSchema.cs` is inert (explicit `ZEnumType` binding
  bypasses the interceptor).

## The batching resolver (`Loaders/ZSchemaResolver.cs`) — read before touching relationship code

`AddSchemaServices` registers `IZResolver → ZSchemaResolver` **scoped per request** and a
`ZDataLoaderRegistry`. `ApiObject.ResolveLocalId/ResolveArray/ResolveKey` call
`Resolver.LoadArray/LoadAll/LoadMany(name, loadFn, key, existing)`:

- one `ZDataLoader` per `TypeName.field` (`SingleDataLoader` for 1:1, `MultiDataLoader` for
  1:many) collects keys in a `ConcurrentBag`;
- `ScheduleResolution` starts a single timer task that waits `ResolveDelayMs` (2–22 ms, grows
  with the square root of pending keys) then calls `Resolve()` on every pending loader — each runs
  the loader's `loadFn(keys)` once, i.e. **one `SELECT … WHERE fk IN (k1..kn)`** per field per
  wave, and keeps resolving until nothing is queued;
- callers poll `Tasks.WaitUntil(() => IsResolved)` every 25 ms (`ZCore/Utils/Tasks.cs`), so the
  minimum latency of a resolved field is one poll tick; deep trees resolve level by level.
- `existing` values (already-loaded navigation lists, or `[NotMapped]` caches) are pre-seeded
  into the loader so they never hit the DB.

Implications: N+1 is solved automatically **inside a GraphQL request**, but only for code that
goes through `Resolve*`/`Resolver.Load*`. Custom `Get…()` methods that call
`Context.QueryFor<T>()…LoadDataModelsAsync()` directly run once per parent object — wrap them in
`Context.Resolver.LoadArray(name, keys => …LoadLookupAsync(...), key, existing)` (pattern:
`TuneCore/Users/TuneUser.cs:161-176`). Outside a request (`WorkDispatcher`, seeds, tests) the
resolver is `ZDefaultResolver` and batching does not exist — see `../ZData/README.md`.

## Writing a query/mutation that scales

1. Expose it as a method on a `ZQueryBase`/`ZMutationBase` subclass returning `Result(...)`
   (`ZCore/Api/ZQuery.cs`); arguments become GraphQL args via `ZInputType<T>`.
2. Build one `IZQueryable` with all `Filter`/`SortAsc`/`Limit` applied; use `Fetch` for the
   navigation properties the fragment will definitely read; let `Resolve*` handle the rest.
3. Never return unbounded lists: add a `Limit` (paging is manual — `Skip/Take` args).
4. `[ApiAuthorize(ZPolicy.X)]` on the method; HotChocolate enforces it before the resolver runs.
5. Subscriptions: `[ApiTopic]` parameter + exactly one `[EventMessage]` parameter (`ZSubscriber`
   reflects into a HotChocolate private field — pinned to HotChocolate 15.1.12; Redis backs pub/sub
   when `REDIS_CONNECTION_STRING` is set, else in-memory).
6. Verify the generated fragment/query in `TuneWeb/User/GraphQL` and the `TuneCore/Types`
   descriptors after running the Development server; then regenerate the StrawberryShake client
   (`TuneClient/README.md`).
